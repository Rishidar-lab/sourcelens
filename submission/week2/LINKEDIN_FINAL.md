Most RAG systems confuse **retrieval** with **evidence**.

A vector store will almost always return its closest match, even when
nothing in the corpus answers the question — and a model asked to answer
from that match will often try anyway. That's the failure mode I built
SourceLens around avoiding.

For Innovation Hacks Week 2, I built **SourceLens**, an evidence-grounded
document assistant with a stricter pipeline: **retrieve → evaluate
evidence sufficiency → generate only when grounded → assemble citations
from retrieval provenance.**

The core design decision: an evidence gate sits **before** generation, not
after. Finding the nearest chunk is never enough on its own — the gate
decides whether the model is even allowed to answer. When evidence doesn't
clear the bar, the system refuses and the language model is never called
at all.

SourceLens ingests PDF/DOCX/TXT/Markdown through a FastAPI backend,
persistent ChromaDB storage, sentence-transformer embeddings, and a React
frontend. Citations come from retrieval provenance — filename, section,
excerpt, score — never generated by the model.

The recorded demo proves both halves live: a supported question gets a
grounded answer with real citations, and an unsupported one gets a
deterministic refusal before generation is ever invoked — same evidence
gate either way.

Evaluated with a 40-question benchmark (Recall@1 94.12%, MRR 0.956) and a
15-case prompt-injection red team. The full local-LLM run also surfaced
real limitations: shared-GPU timeouts and one unresolved prompt-injection
finding, documented rather than hidden. The recording itself needed a
local fallback inference endpoint after GPU contention timed out the
documented default model — disclosed on screen and in the README, not
concealed.
