Most RAG systems confuse **retrieval** with **evidence**.

A vector store will almost always return its closest match, even when
nothing in the corpus actually answers the question — and a model asked to
answer from that match will often try anyway. That's the failure mode I
built SourceLens around avoiding.

For Innovation Hacks Week 2, I built **SourceLens**, an evidence-grounded
document assistant with a stricter pipeline:

**retrieve → evaluate evidence sufficiency → generate only when grounded →
assemble citations from retrieval provenance**

The core design decision: an evidence gate sits **before** generation, not
after. Finding the nearest chunk is never enough on its own — the gate
decides whether the model is even allowed to answer. When the retrieved
evidence doesn't clear the bar, the system refuses and the language model
is never called at all. No guess, no fallback to outside knowledge, no
plausible-sounding answer built on nothing.

SourceLens supports PDF, DOCX, TXT, and Markdown ingestion through a
FastAPI backend, persistent ChromaDB storage, sentence-transformer
embeddings, and a React + TypeScript frontend. Citations are assembled
from retrieval provenance records — filename, section, excerpt, chunk ID,
score — never generated by the model.

I evaluated it with a 40-question golden benchmark and a 15-case
prompt-injection red team over synthetic policy and security documents.
Retrieval-only: Recall@1 94.12%, Recall@3/5 97.06%, MRR 0.956. The full
local-LLM run also surfaced what actually matters: shared-GPU timeouts,
five genuine generation-quality gaps, and one unresolved document-side
prompt-injection finding that survived prompt hardening. I documented
those instead of presenting a flattering but incomplete pass rate.

The lesson from this build: a good RAG demo isn't an answer that sounds
plausible. It's a system that makes evidence, uncertainty, provenance, and
its own failure modes visible.
