## Post

Most RAG systems confuse **retrieval** with **evidence**.

A vector store can return a nearest chunk for almost any question. The harder engineering problem is deciding whether the retrieved material actually supports an answer — and refusing when it does not.

For Innovation Hacks Week 2, I built **SourceLens**, an evidence-grounded document assistant with a stricter pipeline:

**retrieve → evaluate evidence sufficiency → generate only when grounded → assemble citations from retrieval provenance**

SourceLens supports PDF, DOCX, TXT, and Markdown ingestion through a FastAPI backend, persistent ChromaDB storage, sentence-transformer embeddings, and a React + TypeScript frontend. Its citations are built from retrieval records — filename, page or section, excerpt, chunk ID, and score — rather than generated by the model.

I evaluated it with a 40-question golden benchmark and a 15-case prompt-injection red team using synthetic policy and security documents. The retrieval-only run measured Recall@1 of 94.12%, Recall@3/5 of 97.06%, and MRR of 0.956. The full local-LLM run also exposed the limitations that matter: shared-GPU timeouts, five generation-quality gaps, and one unresolved document-side “say X” prompt-injection finding that survived prompt hardening. I documented those findings instead of presenting a flattering but incomplete pass rate.

The main lesson was that a good RAG demo is not just an answer that sounds plausible. It is a system that makes evidence, uncertainty, provenance, and failure modes visible.
