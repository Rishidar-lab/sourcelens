# Week 2 demo script — SourceLens

Target length: 3–5 minutes. Spoken cues in **bold**, on-screen actions in
*italics*. Prepared as an exact recording sequence — no recording exists yet
at the time this script was written; follow it live rather than treating it
as a description of a finished recording.

**Revision note**: this script was revised after the full 40-question
benchmark was actually run against the real LLM. The original draft staged
a live "current-vs-legacy conflict" question as a confident happy-path
demo beat. Running the real benchmark afterward showed that exact scenario
is an open, unresolved finding (`QA-031` — see `docs/FAILURE_ANALYSIS.md`):
the model reliably retrieves both conflicting documents but doesn't
reliably state the conflict. Staging a known-weak scenario as the
happy-path demo would misrepresent measured results, so it's removed as a
live beat and covered honestly in beat 9 instead.

---

**1. Product thesis (20s)**

*Show the running app, header visible.*

> "This is SourceLens — an evidence-grounded document assistant I built for
> Week 2. The core idea: it should never answer from what the model already
> knows. It should only answer from documents you actually give it, with
> citations, and it should refuse cleanly when those documents don't cover
> the question."

**2. Synthetic documents (20s)**

*Show the `qa/corpus/` folder or the `samples/` folder in a file browser
or `ls` — briefly, before switching to the app.*

> "The corpus is synthetic — HR and security policies I wrote for this
> project, including one document that's deliberately adversarial, which
> I'll come back to."

**3. Upload / indexing (30s)**

*Drag the files onto the Knowledge Base panel.*

> "Each document gets parsed, chunked, embedded with a real
> sentence-transformer model — loaded once, not per request — and stored in
> a local vector database."

*Point at chunk counts appearing next to each "Indexed" badge.*

**4. Direct evidence-grounded answer (30s)**

*Type: "How many days per week may an eligible employee work remotely
under the current policy?" Click Ask.*

> "A direct factual question. SourceLens retrieves the relevant chunk,
> passes it to the LLM with an explicit instruction to answer only from
> that evidence, and returns a grounded answer."

**5. Real citation expansion (20s)**

*Click the source card to expand the excerpt.*

> "Every citation traces back to a real retrieval record — filename, page
> or section, the actual excerpt, and a relevance score. Citations are
> constructed from retrieval provenance, not generated by the model."

**6. Unsupported question refusal — the core acceptance test (30s)**

*Type: "Who won the 2018 FIFA World Cup?" Click Ask.*

> "This is the important one. Vector search will still return its closest
> matches from the policy documents — 'closest' isn't the same as
> 'relevant.' SourceLens separates retrieval from evidence. Finding the
> nearest chunk is not enough; the evidence gate decides whether the model
> is allowed to answer. It catches exactly this case and refuses instead of
> guessing. No silent fallback to the model's own knowledge."

**7. Brief architecture (25s)**

> "Backend is FastAPI with a persistent ChromaDB vector store and a real
> sentence-transformer embedding model. LLM backend is pluggable — Gemini,
> any OpenAI-compatible endpoint, or a local Ollama server, which is what's
> running right now. Frontend is React and TypeScript. Everything here —
> the retrieval numbers, the citations, the refusal — is live, not staged."

**8. Evaluation methodology (30s)**

> "This isn't just demoed, it's measured. A 40-question benchmark and a
> 15-case prompt-injection red team, both run against the real configured
> LLM, not simulated. Retrieval recall is 94 to 97 percent. Of the
> questions that actually got a real answer — excluding the ones that hit
> a GPU timeout on this shared dev machine — 76 percent were correct. I
> don't collapse that into one flattering headline number; the full
> breakdown, including what failed and why, is in the repo."

**9. Honest limitations (25s)**

> "Two real things I want to be upfront about. First: it doesn't
> reliably surface a conflict between a current and a superseded policy,
> even when it retrieves both — that's an open finding, not something I
> fixed and I say so directly in the docs. Second: a prompt-injection red
> team found one payload pattern the model still complies with, even after
> I hardened the system prompt against it specifically. Both are documented,
> not hidden."

**10. GitHub repository (10s)**

*Show the repo, README open.*

> "Full source, the backend test suite, the QA benchmark it was measured
> against, and the write-up of exactly what I found and fixed while getting
> this running, are all in the repo — link below."

## Recording notes

- On shared/CPU hardware a real LLM answer can take anywhere from ~30
  seconds to a few minutes (see `docs/EVALUATION.md`) — either record on
  hardware with a faster local model / a hosted API key configured, or cut
  the wait in editing and say so.
- Beats 4–6 are all real acceptance scenarios already verified live in a
  browser this session (see `docs/EVALUATION.md`) — they should behave
  exactly as scripted. Beats 8–9 use exact figures from
  `docs/EVALUATION.md`; re-check them against that file before recording
  in case a later run changes the numbers, rather than trusting this
  script's copy of them indefinitely.
- Do not add a live demonstration of the conflict-handling or
  prompt-injection scenarios as a "look, it works" moment — both are
  documented as open findings specifically because they don't reliably
  work; showing them live risks either contradicting the docs or getting
  lucky on one take in a way that misrepresents the measured rate.
